# Knowledge base

The knowledge base (KB) is a living high-level design (HLD) of the user's
systems and how they connect. Phase 1 builds it, and later phases and routines
keep it current. Everything else in factory (board seeding, monitoring,
infra) reads from it.

It is **always a private GitHub repository in the user's org**:
`github.com/<org>/knowledge`, checked out at `~/workspaces/knowledge`. It is
never local-only and never public. All writes go through `scripts/kb.py`,
which enforces the rules below.

## Provisioning (phase 1)

1. `kb.py ensure-repo <org>` runs `gh repo view <org>/knowledge --json
   visibility,defaultBranchRef,url`, then:
   - **missing**: prints `{"exists": false, "action": "gh repo create ... --private"}`
     and exits `5`. Ask the user (approval gate), then rerun with `--create`,
     which runs `gh repo create <org>/knowledge --private` and clones it.
   - **present and PRIVATE**: clones it to the checkout (or fetches, if the
     checkout already exists and its `origin` is that repo).
   - **present and not PRIVATE** (PUBLIC or INTERNAL): **stop.** Exit `2`,
     nothing is cloned or written. Tell the user, and never continue with a
     local-only KB as a workaround.
   - Output: `{url, path, visibility, created, default_branch, initialized}`.
2. If `initialized` is false (a new, empty repo), run `kb.py init <path>`
   and show the skeleton. After approval, `kb.py propose "Initial skeleton"
   --init` pushes that one commit to `main`. This is the only direct push to
   the default branch that factory ever makes, and `--init` refuses on a repo
   that already has any branch.
3. `ensure-repo` prints a branch-protection recommendation to stderr (require
   a PR + 1 approval, no force-push, secret scanning with push protection).
   Relay it to the user. **Factory never changes org or repo settings.**
4. Record `outputs.kb_repo` / `outputs.kb_path` in state (`references/state.md`).
   **On every resume**, rerun `ensure-repo`: visibility is re-checked, and
   `propose` re-checks it again before every push.

`--name` overrides the repo name and `--path` (or `$KB_DIR`) the checkout.

## Layout

```
README.md           provenance rules (written by init; humans may extend)
index.md            generated by `kb.py index`: one row per system; never hand-edit
systems/<id>.md     one per system: frontmatter + sections (below)
connections.md      edges table + generated mermaid graph + open questions
decisions.md        dated decisions, newest first (infra changes land here too)
```

The system id is a lowercase slug (`[a-z0-9][a-z0-9._-]*`). By default, a repo
maps to the system named after it. A human (or phase 3) can group several
repos into one system with `add-system <id> --repo a --repo b`, and later
ingests respect that mapping.

### `systems/<id>.md`

```markdown
---
name: api
repos: [acme/api, acme/api-worker]
owners: ["@acme/core"]
runtime:
  platform: fly
  environments:
    - name: staging
      id: api-staging
      platform: fly
      url: https://api.staging.acme.dev
      source: infra:fly:app/api-staging
      verified: 2026-09-30
    - name: prod
      id: api-prod
      source: user
      verified: 2026-09-30
monitoring:
  - kind: sentry
    org: acme
    project: api
    mcp: sentry
    source: [acme/api:sentry.properties]
    verified: 2026-09-30
status: active          # candidate | active | deprecated | retired
verified: 2026-09-30    # last time a human confirmed the system as a whole
---

# api

## Purpose
- **purpose**: Public REST API for orders <!-- source: user; verified: 2026-09-30 -->

## Interfaces
- **acme/api exposed ports**: 8080 <!-- source: acme/api; verified: pending -->

## Dependencies
- **acme/api:Cargo.toml cargo deps**: serde, tokio <!-- source: acme/api:Cargo.toml; verified: pending -->
- **uses auth (http)**: [auth](auth.md) <!-- source: acme/api:src/auth.rs:12; verified: pending -->

## Build, run, test
- **acme/api build/run/test**: see [AGENTS.md](https://github.com/acme/api/blob/main/AGENTS.md) <!-- source: acme/api:AGENTS.md; verified: pending -->

## Open questions
- [ ] api: `port` is `8080` (acme/api:Dockerfile) but `9090` (infra:fly:app/api); precedence keeps `9090` (infra:fly:app/api). Confirm or correct. <!-- question: 3f2a9c01de; raised: 2026-09-30 -->
```

- `runtime.environments[]` is keyed by `name`. Infra changes
  (`references/infra-changes.md`) resolve "staging" from it, and an unknown
  staging environment means stop and ask. It is written by `kb.py add-env`.
- The shape of `monitoring[]` is defined in `references/monitoring.md`
  ("Knowledge base integration"). It is written by `kb.py add-monitor` and
  deduped on (`system`, `kind`, `project`).
- A system created by `ingest` starts as `status: candidate, verified:
  pending`. A human (or the user through factory) promotes it.

### Fact lines

Every fact in a body section is exactly one line:

```
- **<key>**: <value> <!-- source: <src>; verified: <YYYY-MM-DD | pending> -->
```

`<src>` is one of:

| source | example | precedence |
|---|---|---|
| `user` | `user` | 3 (highest) |
| `infra:<platform>:<resource>` | `infra:aws:ecs/service/api-prod` | 2 |
| repo path | `acme/api:Cargo.toml`, `acme/api:src/ws.ts:33`, `acme/api` | 1 |
| `gh api ...` | `gh api repos/acme/api` | 1 |

`verified: pending` marks an unconfirmed candidate. A date means that the
source was re-checked (or the user stated it) on that day.

### Precedence and conflicts

`user` > `infra:*` > manifest/code. Rules, as enforced by `kb.py`:

- A fact is **never overwritten by a different source**. When sources
  disagree, a question is appended to `## Open questions`, and it names both
  claims and the one precedence keeps. The board mirrors it as an issue.
- A higher-precedence source that disagrees adds its own line, and that line
  becomes the effective value. A lower-precedence one adds only the question.
- A `source: user` line is never edited or removed by automation.
- The same non-user source reporting a new value updates its own line in
  place, but only when no other source has an opinion on that key.
- A question is resolved by recording the right value with `source: user`
  and ticking `[x]`. Questions are deduped by a content hash.

### `connections.md`

```markdown
## Edges

| from -> to | protocol | auth | source | verified |
|---|---|---|---|---|
| web -> api | ws | ? | acme/web:src/ws-url.ts:33 | pending |
| web -> api | https | oauth | user | 2026-09-30 |

## Graph
<!-- mermaid:begin (generated by kb.py; do not edit) --> ... <!-- mermaid:end -->

## Open questions
```

- A row is keyed by (`from`, `to`, `protocol`), where `from`/`to` are system
  ids or `external:<host>`. Edges inside one system are dropped.
- `ingest` adds `verified: pending` rows only. Several graph edges with the
  same key collapse into one row, which cites the first piece of evidence.
- A `user` or `infra:*` row replaces a lower-precedence row with the same key.
  A candidate never replaces a higher one, and it never adds a row where a
  higher-precedence row already covers that key.
- `auth` names a mechanism (`oauth`, `mTLS`, `api-key header`), never a value.
- The mermaid block is regenerated from the table on every write and by
  `kb.py index`. Pending edges are dashed (`-.->`), confirmed ones solid.
  Other `##` sections that humans add are preserved.

### Secrets

Hostnames, ports, account/project ids and topology are fine: the repo is
private. **Secrets never are.** `kb.py` refuses (exit `3`, nothing written,
`--force` does not bypass it) any value or file that matches:

| pattern | example |
|---|---|
| AWS access key | `AKIA...`, `ASIA...` |
| Google API key | `AIza...` |
| GitHub token | `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_` |
| `sk-` API keys | OpenAI/Anthropic/Stripe-style `sk-...` |
| Slack token | `xox[abprs]-...` |
| JWT | `eyJ...eyJ...sig` |
| assignments | `password=`, `secret:`, `token=`, `api_key=` ... |
| private keys | `-----BEGIN ... PRIVATE KEY-----` |
| service-account JSON | `"type": "service_account"`, `"private_key":` |

Env var **names** (`SENTRY_AUTH_TOKEN`) are fine. Their values are not.

## `scripts/kb.py`

It uses the stdlib only, and shells out to `git` and `gh`. It prints JSON on
stdout. Global flags: `--kb <path>` (default `$KB_DIR`, then
`~/workspaces/knowledge`) and `--force` (write on a dirty checkout).

| command | does |
|---|---|
| `init <path>` | skeleton (README with provenance rules, `index.md`, `connections.md`, `decisions.md`, `systems/`) and the initial commit on `main`. Refuses a non-empty directory without `--force`. Idempotent. |
| `add-system <id> [--repo R]... [--owner O]... [--purpose P] [--status S] [--runtime platform] [--source user]` | create or extend `systems/<id>.md` |
| `add-env <system> <name> --id ID [--platform P] [--url U] --source S` | upsert `runtime.environments[]` by name. A non-user disagreement becomes a question, `user` wins, and a `user` entry is never touched by others |
| `add-monitor <system> --kind K [--project P] [--org O] [--site S] [--url U] [--mcp alias] --source owner/repo:path\|user ...` | exactly as in `references/monitoring.md` |
| `add-fact <system> --section purpose\|interfaces\|dependencies\|build --key K --value V --source S [--pending]` | one fact line, with the precedence rules above |
| `add-connection <from> <to> --protocol P [--auth A] --source S` | one edges row plus the mermaid graph |
| `ingest graph.json` | `repos[]` become candidate systems (unless an existing system already lists the repo) plus pending facts (languages, default branch, AGENTS.md pointer, deps per manifest file, ports). `edges[]` become pending connection rows plus `uses <system>` dependency facts. Never deletes, never touches `user` lines, idempotent (a rerun on the same graph commits nothing) |
| `index` | regenerate `index.md` and the mermaid graph |
| `stale [--days 30]` | `{stale[], pending[], questions[], counts}`: dated items older than N days, pending candidates, open questions |
| `ensure-repo <org> [--name knowledge] [--path P] [--create]` | provisioning (above). Exit `2` on a non-private repo, `5` when it is missing and `--create` was not given |
| `propose "<title>" [--body B] [--init] [--allow-multiple]` | push local commits beyond `origin/<default>` as `factory/<slug>`, `gh pr create --base <default>`, then reset local `main` to origin. Refuses when the repo is not private (2), when `--init` is used on a non-empty repo (5), and when another `factory/*` PR is open (5, unless `--allow-multiple`) |
| `board-ops [--project-id ID] [--existing project_get.json] [--with-index] [--days 30]` | prints `project_update` input: `add_issue` per open question and per system file with stale items, each tagged `<!-- kb:question:<id> -->` / `<!-- kb:stale:<hash> -->` and deduped against `--existing`. `--with-index` adds `set_project.description = index.md` |

Write commands commit locally, one commit per command, and never push:
pushing is only done by `propose`. They refuse a dirty checkout (exit `4`)
unless `--force` is given, and take a non-blocking lock on `.git/kb.lock`, so
a concurrent writer gets exit `6` (single writer, see
`references/parallelism.md`). Exit codes: `0` ok, `1` usage/validation, `2`
not private, `3` secret refused, `4` dirty or not empty, `5` precondition
(missing repo, open PR, `--init` misuse), `6` locked.

### Typical phase-1 run

```bash
kb.py ensure-repo acme                          # exit 5 -> ask -> --create
kb.py init ~/workspaces/knowledge               # only if initialized=false
kb.py propose "Initial skeleton" --init         # after approval
repo_graph.py ~/workspaces/* --org acme --out /tmp/graph.json
kb.py ingest /tmp/graph.json
kb.py add-system api --repo acme/api --purpose "..." --source user   # from the phase-3 answers
kb.py propose "Ingest 12 repos"
kb.py board-ops --project-id <kb-project> --with-index > ops.json   # -> project_update
```

### Forge project "Knowledge base"

The KB is mirrored by a Forge project named **Knowledge base**. Its
description is `index.md` (`board-ops --with-index`). Its issues are the open
questions and the stale facts, one per system file. Routines run `stale` and
`board-ops`, then apply the operations with `project_update` after dedupe
against `project_get`. Closing a board issue does not change the KB: the
answer has to land as a KB PR.

## `graph.json` (repo graph)

Produced by `scripts/repo_graph.py` from local checkouts. It is the machine-readable
input that the knowledge-base phase turns into `systems/*.md` and `connections.md`.
Regenerate it at any time: scanning is deterministic, and `--jobs N` output is
identical to `--jobs 1` output apart from `generated_at`.

```
repo_graph.py <path>... --org <org> [--jobs 8] [--out graph.json] [--refresh]
```

```json
{
  "version": 1,
  "generated_at": "2026-09-30T07:30:00+00:00",
  "repos": [
    {
      "full_name": "acme/api",
      "path": "/home/me/workspaces/api",
      "default_branch": "main",
      "languages": ["Rust"],
      "manifests": [ { "file": "Cargo.toml", "kind": "cargo", "deps": ["serde", "tokio"] } ],
      "ports": [8080],
      "errors": []
    }
  ],
  "edges": [
    { "from": "acme/web", "to": "acme/api", "kind": "url", "protocol": "ws",
      "evidence": "config/app.json:2", "source": "repo_graph" }
  ],
  "url_refs": [
    { "from": "acme/web", "scheme": "ws", "host": "localhost", "port": 8080,
      "evidence": "config/app.json:2" }
  ]
}
```

### `repos[]`

| field | required | meaning |
|---|---|---|
| `full_name` | yes | `owner/name` from `remote.origin.url`; if there is no GitHub remote, falls back to `<org>/<dirname>` |
| `path` | no | absolute local checkout path |
| `default_branch` | no | from `origin/HEAD`; omitted when unknown |
| `languages` | yes | ordered by file count, highest first |
| `manifests` | yes | `{file, kind: cargo\|npm\|pyproject\|go, deps: [direct dep names]}` |
| `ports` | yes | ports the repo exposes: Dockerfile `EXPOSE`, compose `ports:`, listen defaults in non-test source |
| `errors` | yes | per-repo scan problems; one bad repo never fails the run |

### `edges[]`

| field | required | meaning |
|---|---|---|
| `from` | yes | `full_name` of the repo containing the evidence |
| `to` | yes | `full_name`, or `external:<host>` (reserved; not emitted yet) |
| `kind` | yes | `submodule` (`.gitmodules` url), `manifest` (`github.com/<org>/x` in a manifest), `workflow_uses` (`uses: <org>/x` in `.github/workflows`), `image` (`image:`/`FROM` `<org>/x`), `url` (`ws/http(s)://host:port` in config or non-test source where the port is exposed by another scanned repo) |
| `protocol` | no | URL scheme, for `url` edges only |
| `evidence` | yes | `file:line`, relative to the `from` repo root |
| `source` | yes | always `repo_graph` for this script; other producers use their own value |

`url_refs[]` holds the raw URL hits that `url` edges are resolved from. They are kept
so that a later incremental run, which scans a new repo exposing the port, can
resolve edges without rescanning the referring repo.

### Merge semantics (`--out`)

- Repos already present in `--out` are kept as they are and not rescanned, unless
  `--refresh` is passed.
- For every rescanned repo, its old edges and `url_refs` are dropped and replaced.
- `url` edges are recomputed on every run from the full `url_refs` and `ports` sets.
- The write is atomic (tmp file + rename).

Per-repo timing is printed to stderr.

Scope: local checkouts only. Org enumeration, `gh api` metadata and activity
metrics are added by `repo_graph.py` in a later issue.
